# Astraudit rule book

This document lists **every** detector Astraudit ships and exactly
what triggers it. The audit you see in the browser is generated by
running these rules against the public files + metadata of the
repository under review — there is no AI, no telemetry, no
inference-by-vibes. If a rule fires on your repo and you don't know
why, this page is the source of truth.

## How to read this document

- **Rule ID** — a stable identifier emitted by the audit engine.
- **Triggers when…** — the precise condition that flips the rule on.
- **Severity** — `critical` / `high` / `medium` / `low` / `info`.
  Drives sort order in the Findings panel.
- **Category** — maps to the eight scored categories
  (Documentation, Structure, Code Quality, Security, Maintenance,
  Developer Experience, Ecosystem, CI/CD).
- **Recommendation** — the actionable hint we attach to the finding.

Some detectors don't emit findings — they surface as **panel
outputs** in the dashboard's Insights or Story sections. Those are
listed separately at the end of the doc.

> Every rule below runs **only** against public GitHub metadata,
> public file contents, and free public registry endpoints. No
> private repositories, no credentials, no third-party AI APIs.

## Score & grade model

The audit produces a 0–100 score across eight categories, weighted
by how universal each category is for adopters. Each category has a
`max` (the cap if the category is "fully covered") and a `score`
(what we observed). Letter grades come from the total:

| Total score | Grade | Verdict tone |
|------------:|:-----:|:-------------|
| 90–100      | A     | Adopt with confidence |
| 75–89       | B     | Solid, with room to tighten |
| 60–74       | C     | Useable, expect rough edges |
| 45–59       | D     | Risky — read the findings carefully |
| 0–44        | F     | Avoid for production use |

Status ribbons in the audit graph map onto the same model:

| Status         | Meaning |
|----------------|---------|
| `Strong`       | Category ≥ 80 % of its max |
| `Partial`      | 50 – 79 % |
| `Missing`      | < 50 % |
| `Info`         | Informational signal, no score impact |
| `Not detected` | Detector did not have enough data |

## Findings catalog

The findings list below is the **source-of-truth** for the
`riskEngine.ts` module. Every entry corresponds to one
`Finding` produced during a real audit. Entries are grouped by the
category they score against.

### Documentation

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `doc-no-readme` | The repository ships no `README.*` of any kind. | high |
| `doc-readme-too-short` | A README exists but is shorter than ~200 characters of body content (badges + headings stripped). | medium |
| `doc-no-setup` | The README has no setup / install / quickstart heading or call-out. | medium |
| `doc-no-usage` | The README has no usage / example / demo section. | low |
| `doc-no-contributing` | No `CONTRIBUTING.md` (or `.github/CONTRIBUTING.md`) is present. | low |

### Structure

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `struct-root-crowded` | More than ~20 files live at the repository root, suggesting the project hasn't been broken into folders. | low |

### Code Quality

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `quality-no-tests` | No test files match any of the recognised patterns (`__tests__/`, `*.test.*`, `*.spec.*`, `pytest.ini`, `Cargo.toml [[test]]`, etc.) AND no test script is declared. | high |

### Security

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `sec-no-license` | No `LICENSE` / `LICENSE.md` / `COPYING` file is present in the root or `licenses/` folder. | critical |
| `sec-committed-env` | A `.env`, `.env.local`, `.env.production`, etc. is committed outside any test-fixture / docs folder. | high |
| `sec-suspicious-file` | A filename matching one of the suspicious patterns (`secret`, `credentials`, `private_key`, `kubeconfig`, etc.) is committed. | medium |
| `sec-no-security-md` | No `SECURITY.md` is present. | medium |
| `sec-no-dep-automation` | Neither `dependabot.yml` nor a Renovate config is detected. | low |

### Maintenance

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `maint-inactive` | The repository's most recent push is more than 18 months old. | medium |

### Developer Experience

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `dx-no-clear-setup` | The repo lacks both a `package.json scripts.start` (or equivalent `make`/`task`/`just` recipe) AND any first-run instructions in the README. | low |

### Ecosystem

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `eco-no-lockfile` | A package manifest (`package.json`, `Cargo.toml`, `Pipfile`, `Gemfile`, `composer.json`, `go.mod`) is present but no matching lockfile is committed. | medium |

### CI/CD

| Rule ID | Triggers when… | Severity |
|--------|----------------|---------|
| `ci-no-pipeline` | No GitHub Actions / GitLab CI / CircleCI / Travis / Jenkins / Drone config is detected anywhere in the repo. | medium |

## Panel outputs (no finding emitted)

These detectors don't fire findings — they enrich the dashboard's
Insights / Story / Topic / Registry / License panels with
contextual signals.

### Readability (Phase 3.1)

Computes Flesch-Kincaid Grade Level + Flesch Reading Ease on the
prose extracted from the README. Strips fenced + indented code,
inline code, badges, image embeds, HTML, table rows, link URLs
(keeps labels), heading markers, blockquotes, list markers,
emphasis, and reference-link definitions. Returns `null` for
prose shorter than 30 words or fewer than 2 sentences. Bucketed
into `elementary` / `easy` / `standard` / `dense` / `academic`.

### Dependabot config (Phase 3.2)

Parses `.github/dependabot.yml` (or `.yaml`) — handles `version: 2`
files only. Surfaces every `updates[]` entry with its
`package-ecosystem`, `directory`, `schedule.interval`,
`open-pull-requests-limit`, `target-branch`, and group count. The
parser tolerates block mappings, block sequences, inline scalars,
inline-flow arrays, full-line + trailing comments. Anchors,
aliases, tags, and multi-line block scalars are NOT supported
(returns `null`).

### CODEOWNERS density (Phase 3.3)

Parses every line of `CODEOWNERS` (or `.github/CODEOWNERS`,
`docs/CODEOWNERS`, `.gitlab/CODEOWNERS`). Classifies each owner as
`user` (`@octocat`), `team` (`@org/team`), `email`
(`user@example.com`), `role` (GitLab `@@developer`), or `unknown`.
GitLab section headers (`[Section]`, `[Section][5]`, `^[Section]`)
are tolerated and counted. Coverage % is computed against the
repo's blob list using the documented gitignore-style globs (`*`
not crossing slashes, `**` crossing them, `/` prefix anchoring,
trailing `/` for dir match), implementing GitHub's
"last-matching-pattern wins" precedence.

### Security policy quality (Phase 3.4)

Parses `SECURITY.md` and grades it via OpenSSF Scorecard's
signal scheme: `placeholder` (no contact channel), `basic` (channel
only), `good` (channel + ≥ 40 words + vulnerability terminology),
`complete` (channel + ≥ 80 words + a measurable timeline like
"within 30 days"). Recognised channels: private email, GitHub
Security Advisories (URL + phrase), HackerOne, Bugcrowd, Open Bug
Bounty, PGP keys (inline armored block + key URL).

### Runtime contract (Phase 3.5)

Reads `engines.node` from `package.json`, classifies into
`missing` / `any` / `modern` / `current` (Node 22 LTS) / `aging`
(EOL Node 18-20) / `ancient` (Node ≤ 16). Also surfaces the
Corepack `packageManager` pin, the `type` field, and every
`peerDependencies` entry with `peerDependenciesMeta.optional`
honoured.

### CHANGELOG cadence (Phase 3.6)

Walks every heading line (`#`, `##`, `###`) looking for dated
release entries — accepts Keep-a-Changelog (`## [1.0.0] - 2024-01-15`),
Conventional Changelog (`## 1.0.0 (2024-01-15)`), v-prefix, slash
separator. Computes mean + median delta in days and a coarse
cadence bucket: `frequent` (≤ 14 d) / `regular` (≤ 60 d) /
`occasional` (≤ 180 d) / `rare` (≤ 365 d) / `dormant`. Stale
projects (latest > 540 d) collapse to `dormant` regardless of
historical cadence.

### Topic-driven contextual rules (Phase 3.7)

Each rule fires when a known GitHub topic is present and verifies
the contract that topic conventionally implies. Rules:

| Topic                           | Contract verified |
|---------------------------------|-------------------|
| `cli`, `command-line`, `terminal`, `tui` | `bin` entry in `package.json` |
| `eslint-plugin`                 | Name `eslint-plugin-*` + `eslint` peer + `eslint-plugin` keyword (graded met / partial / missing) |
| `babel-plugin`                  | Name `babel-plugin-*` + `@babel/core` peer |
| `postcss-plugin`                | `postcss` peer + `postcss-plugin` keyword |
| `react-component` / `vue-component` / `svelte-component` | Framework declared in `peerDependencies` |
| `monorepo`                      | `workspaces` field OR `pnpm-workspace.yaml` |
| `typescript`                    | `tsconfig.json` present |
| `github-action`                 | Root `action.yml` (or `.yaml`) |
| `vscode-extension`              | `engines.vscode` declared |
| `chrome-extension` / `browser-extension` | Root `manifest.json` |
| `electron`                      | `electron` in dependencies |
| `webpack-plugin` / `vite-plugin` / `rollup-plugin` / `esbuild-plugin` | Bundler declared as peer dependency |

### Public registry signals (Phase 3.8)

For up to 12 npm + 10 PyPI + 10 crates.io top-level dependencies
per audit, the dashboard pulls latest version, last publish date,
deprecation flag (npm), and 90-day download count (crates.io)
from the public, unauthenticated, browser-CORS-friendly endpoints:

- `https://registry.npmjs.org/{name}`
- `https://pypi.org/pypi/{name}/json`
- `https://crates.io/api/v1/crates/{name}`

Results cached in `localStorage` for 24 hours. Each row is bucketed
`fresh` (≤ 90 d) / `recent` (≤ 365 d) / `stale` (≤ 730 d) /
`abandoned`.

### License tone (Phase 3.9)

Classifies the repo's own license + every dependency license
(pulled from the registry endpoints above) into `permissive` /
`weak-copyleft` / `strong-copyleft` / `public-domain` /
`proprietary` / `none` / `unknown`. Honours SPDX expressions:
`MIT OR Apache-2.0` collapses to the most-permissive alternative,
`AND` to the most-restrictive. Findings:

| Rule ID                     | Triggers when… | Tone |
|-----------------------------|----------------|------|
| `strong-copyleft-deps`      | Any dependency is GPL / AGPL family. | `critical` if repo is permissive / public-domain / undeclared, else `warning` |
| `weak-copyleft-deps`        | Any dependency is LGPL / MPL family. | `info` (linking is usually fine) |
| `proprietary-deps`          | Any dependency is BUSL / Elastic / SSPL etc. | `warning` |
| `unclassified-deps`         | ≥ 25 % of classified deps have an unrecognised license string. | `info` |

## Opt-in rule packs (Roadmap Monat 5)

Rule packs are **off by default**. The canonical audit at
`https://beko2210.github.io/astraudit/#/audit/owner/repo` runs the
core ruleset above and nothing else, so the score / verdict stay
comparable across visitors and across snapshots.

Visitors who want extra coverage opt in via the `?rules=` URL
flag (comma-separated, in any order):

```
https://beko2210.github.io/astraudit/?rules=a11y,i18n,ts,monorepo#/audit/owner/repo
```

The Settings dialog (M5.5) exposes the same toggles as
convenience checkboxes. The URL flag remains the source of truth
so a shared link always reproduces the same findings.

Pack findings flow through the same severity ordering as the core
ones, sit naturally in the dashboard's Findings panel, and never
influence the category score (which stays comparable across
configurations).

### `?rules=a11y` — Accessibility

Surfaces signals about whether a repository takes accessibility
seriously. Useful when reviewing a UI library or a hosted web
app you're considering depending on.

| Rule ID | Triggers when… | Severity |
|---|---|:--:|
| `a11y-readme-img-no-alt` | The README ships markdown images `![](url)` or inline `<img>` tags without an `alt=` attribute. `alt=""` is treated as a deliberate decorative declaration and **not** flagged. | `low` (1–3 images) / `medium` (4+) |
| `a11y-tooling-detected` | `package.json` declares any of: axe-core, `@axe-core/react`, `@axe-core/playwright`, `@axe-core/webdriverjs`, `@axe-core/cli`, `jest-axe`, `vitest-axe`, `react-axe`, `cypress-axe`, `@cypress/axe`, `pa11y`, `pa11y-ci`, `wave-evaluator`, `eslint-plugin-jsx-a11y`, `eslint-plugin-vuejs-accessibility`, `react-aria`, `react-aria-components`, `@react-aria/*`, `@react-stately/*`, `@headlessui/react`, `@headlessui/vue`, `@radix-ui/*` (primitive / dialog / dropdown-menu / popover / tooltip / tabs), `reakit`, `ariakit`, `@ariakit/react`. | `info` |
| `a11y-no-tooling` | The repo depends on a UI framework (React, Vue, Svelte, Solid, Preact, Angular, Lit, Qwik, Marko, Mithril, HTMX) but ships none of the libraries above. | `low` |
| `a11y-docs-found` | An `ACCESSIBILITY.md` or `A11Y.md` is present at the repo root (case-insensitive). | `info` |
| `a11y-no-docs` | UI project (see above) with **no** a11y doc **and** no `accessibility` / `a11y` / `aria` / `screen reader` / `wcag` mention in `CONTRIBUTING.md`. | `low` |

Trigger example: `?rules=a11y#/audit/facebook/react` surfaces the
tooling + docs findings. `?rules=a11y#/audit/some/cli-only-repo`
is a no-op because the UI-framework gate isn't satisfied.

### `?rules=i18n` — Internationalisation

Surfaces signals about whether a repository is set up for
international audiences.

| Rule ID | Triggers when… | Severity |
|---|---|:--:|
| `i18n-libraries` | `package.json` (any dep scope) declares one of: `i18next`, `react-i18next`, `next-i18next`, `i18next-browser-languagedetector`, `next-intl`, `react-intl`, `@formatjs/intl`, `formatjs`, `@lingui/core`, `@lingui/react`, `@lingui/macro`, `lingui`, `vue-i18n`, `@nuxtjs/i18n`, `nuxt-i18n`, `svelte-i18n`, `polyglot`, `node-polyglot`, `node-gettext`, `gettext-parser`, `i18n`, `rosetta`. | `info` |
| `i18n-locale-coverage` | Locale codes are extracted from files in conventional locale folders (`locales/`, `locale/`, `i18n/`, `messages/`, `translations/`, `lang/`, `langs/`, `translation/`). Recognises `.po`, `.pot`, `.mo`, `.xliff`, `.xlf`, `.arb`, `.properties`, plus JSON / YAML when the basename is an ISO 639-1 code. | `info` |
| `i18n-readme-translations` | Alternate README files exist at the repo root: `README.de.md`, `README_ja.md`, `README-zh.md`, etc. Nested READMEs (`packages/foo/README.de.md`) are skipped because they're usually package docs, not translations. | `info` |
| `i18n-no-setup` | The repo ships a `package.json` but no i18n library, no locale folder, and no translated README. | `low` |
| `i18n-readme-english-only` | The repo HAS an i18n library or non-English locales but ships an English-only README. | `low` |

Trigger example: `?rules=i18n#/audit/i18next/i18next` surfaces
library + locale-coverage findings. `?rules=i18n#/audit/some/empty-repo`
is a no-op.

### `?rules=ts` — TypeScript strictness

Reads `tsconfig.json` (JSONC tolerant — comments + trailing commas
stripped before parsing) and reports on the project's effective
strictness posture.

| Rule ID | Triggers when… | Severity |
|---|---|:--:|
| `ts-no-tsconfig` | The repo contains `.ts` files or has `typescript` in deps, but no `tsconfig.json` at the root. | `low` |
| `ts-strict-on` | `compilerOptions.strict` is `true`. Lists any explicit per-family disables (e.g. `"strict": true, "strictNullChecks": false`). | `info` |
| `ts-strict-off` | `strict` is missing **and** no individual strict-family flag is set. TypeScript runs in its loosest mode. | `medium` |
| `ts-strict-partial` | Some strict-family flags are enabled individually but not `"strict": true`. Lists which. | `low` |
| `ts-extra-strict-on` | Any of the modern recommended extras is enabled: `noUncheckedIndexedAccess`, `noImplicitOverride`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noFallthroughCasesInSwitch`, `noImplicitReturns`. | `info` |
| `ts-extra-strict-suggest` | `strict: true` is on but none of the extras above are. Soft nudge. | `low` |

Note: `extends` chains are **not** resolved. A tsconfig that
defers strictness to `@tsconfig/strictest` reads here as
"strict not explicit" — surfaced honestly rather than guessed.

Trigger example: `?rules=ts#/audit/microsoft/typescript` shows
strict-on + extras-suggest. `?rules=ts#/audit/some/python-repo`
is a no-op because there are no TS files and no tsconfig.

### `?rules=monorepo` — Monorepo health

Surfaces monorepo structure + orchestrator signals.

| Rule ID | Triggers when… | Severity |
|---|---|:--:|
| `monorepo-detected` | Any unambiguous monorepo signal: a `workspaces` field in `package.json` (array or `{packages: […]}` form), a `pnpm-workspace.yaml`, an orchestrator config file, or multiple inner `package.json` files under `packages/` / `apps/`. | `info` |
| `monorepo-no-orchestrator` | Workspaces declared but no `turbo.json`, `nx.json`, `lerna.json`, `rush.json`, or `moon.yml`. Without one, cross-package builds run sequentially with no caching. | `low` |
| `monorepo-packages-not-declared` | Inner `package.json` files under `packages/` or `apps/` exist but the root has no `workspaces` field **and** no `pnpm-workspace.yaml`. The package manager isn't linking them. | `low` |
| `monorepo-multiple-orchestrators` | Two or more orchestrator config files (e.g. `turbo.json` + `nx.json`). Usually an unfinished migration. | `low` |
| `monorepo-changesets-detected` | The `.changeset/` folder is present at the repo root. | `info` |

Inner-package walk matches `packages/*/package.json` and
`apps/*/package.json` **one level deep only** — nested
`packages/foo/sub/package.json` is correctly skipped.

Trigger example: `?rules=monorepo#/audit/vercel/turbo` surfaces
detected + changesets findings. `?rules=monorepo#/audit/some/single-package-repo`
is a no-op.

## Operating constraints (also baked into every rule)

Every rule above conforms to the four constraints that define the
project. New rules are accepted only if they pass all four:

1. **Browser-only.** No backend, no serverless functions, no
   managed databases. The audit runs in the user's tab and dies
   with it.
2. **Free, forever.** No paid APIs, no metered services. Every
   data source is either GitHub's public unauthenticated endpoint
   or a free public registry.
3. **Public repositories only.** The audit cannot — and will never
   — see anything that requires a private credential. Optional
   user-provided GitHub PATs stay in the user's `localStorage` and
   are sent only to GitHub's own hosts.
4. **Rule-based.** No AI, no LLMs, no inference. Every finding has
   a deterministic trigger you can read in this document and
   reproduce yourself.

## How to propose a new rule

Open a GitHub issue with:

1. The user need in one or two sentences.
2. The data Astraudit would need to satisfy it (which file, which
   API, which signal).
3. A check against the four constraints above.
4. A draft rule entry in the same format as the catalog above
   (rule ID, triggers, severity, category, recommendation).

Rules that clear all four constraints land on the roadmap. Rules
that don't are either reframed or recorded in the
[anti-roadmap](../ROADMAP.md#anti-roadmap--things-astraudit-will-never-do).
